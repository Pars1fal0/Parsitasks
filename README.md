# Parsitasks

### Эксплуатация И Восстановление (0.34.17)

Восстановление пароля проверяет сессию сервером до показа формы, убирает токены
из URL и сохраняет режим при перезагрузке текущей вкладки. Просроченные ссылки
не заменяют существующий аккаунт. Проверка: `npm run test:auth-recovery`, все
HTTP-запросы подставные; реальные письма пользователям не отправляются.

Публичный мониторинг включён в GitHub. Добавлены уведомления об инцидентах без
данных пользователей, проверяемая зашифрованная упаковка существующих экспортов
и workflow отката проверенной сборки без отката базы. Для автоматизированного
выпуска и отката ещё нужны секреты Cloudflare в GitHub. SMTP, CAPTCHA и полное
восстановление базы не объявляются настроенными.

Инструкции и фактические ограничения: [OPERATIONS.md](OPERATIONS.md).

### Сохранность Аккаунта (0.34.16)

Восстановление облачной версии выполняется атомарно: проверяется владелец и
ревизия, предыдущее состояние сохраняется независимо от пятиминутного интервала
автоматических снимков. Конфликт или отсутствие RPC не приводит к обычной
перезаписи. Более новая схема данных требует обновить приложение.
Локальные изменения, сделанные во время ожидания восстановления, не заменяются
ответом сервера; приложение объясняет, как объединить или повторить загрузку.

Удаление аккаунта сначала очищает изображения через Storage API. Ошибка очистки
останавливает удаление аккаунта; часть уже удалённых изображений не восстанавливается.
SQL не удаляет Storage-метаданные напрямую и не допускает удаление аккаунта с
оставшимися изображениями. Локальные данные и файлы пользователя в Drive остаются.
Правила Storage дополнительно проверяют существование аккаунта: старый JWT
удалённого пользователя не даёт доступа к изображениям. Запись изображения и
удаление аккаунта используют совместимые блокировки строки владельца.

**При развёртывании новой базы примените** `database/20261006-account-recovery.sql` после миграции
надёжности от 5 октября, затем `database/20261006-storage-lifecycle.sql`.
Запустите обе соответствующие `*-verify.sql`: все результаты должны быть `true`.
Миграция Storage должна быть последней, чтобы сохранить блокировку удаления.
В production обе миграции применены 6 октября 2026 года; проверки каталогов
вернули `true`. Реальная изоляция двух тестовых аккаунтов и конкурентные запросы
managed Storage требуют отдельной проверки; личный аккаунт для них не использовался.
Полный порядок выпуска и незакрытые условия
коммерческого запуска: [LAUNCH_CHECKLIST.md](LAUNCH_CHECKLIST.md).

Проверки: `npm run test:sql-isolation` на искусственных аккаунтах PostgreSQL и
`npm run test:account-recovery` в изолированных browser-профилях с подставным
облаком. Личные аккаунты не используются. Live-проверки больше не создают
контрольные задачи и читают только два выбранных тестовых аккаунта.

Импорт настроек проверяет формат, версию и размер JSON (до 256 КБ), не меняет
настройки, отсутствующие в файле, и отменяется при смене аккаунта. Ошибки записи
не показываются как успешный импорт. Часовой пояс и доступ ChatGPT откатываются
при отказе сохранения. Проверка: `npm run test:settings-reliability`.

`npm run check:availability` дополнительно проверяет Supabase Auth и Data API
без входа и чтения задач. Проверка не подтверждает доставку писем, полноценную
синхронизацию или восстановление всего production-проекта.

Закрыты предупреждения текущего npm audit обновлениями MCP SDK 1.32.1,
`sharp` 0.35.5 и `proxy-addr` 2.0.8. Overrides сохраняют исправленные версии
в зависимостях Agents/Miniflare, пока upstream закрепляет прежние версии.

Документы в `docs/` и других вложенных папках сохраняются локально и исключены
из Git. В репозитории остаются корневые `README.md`, `CHANGELOG.md`, `SECURITY.md`
и `LAUNCH_CHECKLIST.md`.
Локальный роадмап: `docs/ROADMAP.md`.

### Развёрнутый Календарь (0.34.15)

- Таймлайн разворачивается на весь экран приложения; дата, день/неделя и выход остаются сверху. Задачи без времени и сроки открываются отдельной панелью.
- При выходе сохраняются видимое время и масштаб. «Назад» и Escape закрывают развёрнутый режим; несохранённая форма требует подтверждения.
- На телефоне удержание выделяет задачу: ручки меняют начало и окончание с шагом 15 минут. Прокрутка одним пальцем и масштабирование двумя сохраняются.
- Уменьшение числовой привычки доступно рядом со значением. Дополнительные прибавки раскрываются без перекрытия других привычек, повторные изменения используют актуальные данные.
- Мобильные кружки выполнения имеют размер 28 px с областью нажатия 44 px и не перекрывают перетаскивание.

Проверка: `npm run test:calendar-expanded`, `npm run test:calendar-touch`, `npm run test:habit-numbers`, `npm run test:mobile-completion`, только изолированные профили. Эмуляция Chromium не заменяет проверку на Android/iOS.

### Мобильные Сценарии (0.34.13)

- В учёбе история, семестры и чередование недель находятся в меню. Расписание имеет одну мобильную навигацию дат; создание ДЗ остаётся над списком.
- Загрузка материалов выровнена с поиском и фильтром. Палитры доски остаются в границах полотна, а мобильный таймлайн оставляет больше места для прокрутки страницы.
- Подзадачи занимают всю строку задачи. У мобильных форм прокручивается содержимое, а сохранение и отмена остаются доступными при уменьшении видимой высоты.
- Короткие соседние события выбираются через читаемый список без изменения их визуальной длительности. В меню недельного календаря доступен режим трёх дней.
- Дополнительные прибавки числовых привычек раскрываются по запросу. Чтение заметки скрывает сохранение и удаление; поиск использует всю ширину строки.
- Повторяющиеся выполнения архива можно группировать. Импорт показывает таблицу количеств и отдельное предупреждение о замене; отмена сохраняет текущее пространство.
- Сводка периода стоит перед графиками, средний дневной процент подписан отдельно от общей доли выполненных задач. Для годового heatmap есть выбор даты с подробностями.

Проверка: `npm run test:mobile-workspace`, `npm run test:mobile-layout`, `npm run test:study-materials`, только изолированные профили.
Меньшая высота экрана моделирует клавиатуру, но не заменяет Android/iOS-проверку.
Фоновая доставка браузерных напоминаний не добавлена: открытая вкладка по-прежнему необходима.

### Мобильный Календарь (0.34.12)

Два пальца масштабируют часы, один прокручивает сетку, удержание переносит задачу.
Мобильные действия доступны без открытия редактора. Параметры сетки и слой занятий
находятся в меню календаря; масштаб сохраняется только на устройстве.
Проверка: `npm run test:calendar-touch`, без личных и production-аккаунтов.

### Исправления Надёжности (0.34.11)

Одновременно открытые вкладки объединяют записи перед сохранением и не могут
записывать в пространство другого аккаунта. Конфликтующие заметки сохраняются
отдельными копиями, варианты дневной записи — в истории. Черновики редакторов
разделены по вкладкам: перезагрузка их сохраняет, закрытие вкладки может удалить
несохранённый черновик. Это не замена сохранению и резервной копии.

Напоминания о работе и сдаче независимы. В браузере уведомления требуют открытой
вкладки; в Electron приложение должно оставаться запущенным, в том числе в трее.
На телефоне календарная неделя показывает выбранный день и переключатели всех
семи дат. Полная недельная сетка остаётся доступна отдельно; короткие события
имеют меню завершения и редактирования. Переход к делам без времени находится
над сеткой, сами дела остаются ниже неё.

**Перед публикацией этих изменений примените**
сначала `database/20261005-reliability-backup.sql`, затем
`database/20261005-reliability.sql` в Supabase SQL Editor. Первый файл сохраняет
состояния, снимки и прежнюю trigger-функцию в закрытой схеме `parsitasks_ops`;
он не заменяет независимую внешнюю резервную копию проекта. Миграция идемпотентна,
но должна пройти проверку на отдельной базе и применяться с резервной копией.
После применения выполните `database/20261005-reliability-verify.sql`: все
логические столбцы должны быть `true`. Он не возвращает личное содержимое.
`npm run test:sql-reliability` выполняет миграцию на отдельном PostgreSQL (PGlite)
с искусственными аккаунтами. Это не заменяет проверку RLS и восстановления
на отдельном Supabase-проекте. Для новой базы используйте полный
`database/supabase-schema.sql`.

- RPC ограничивает MCP до 120 запросов в минуту на аккаунт во всех Worker-инстансах. Отсутствие RPC или ошибка проверки приводит к 503; исчерпание лимита — к 429.
- Клиент ограничивает отправку состояния 4 MiB JSON, старые UI-данные — 256 KiB. Серверные пределы 8 MiB/512 KiB учитывают отличие представления JSON в Postgres. Это предел записи, не обещание доступного места в тарифе.
- Автоматический снимок создаётся не чаще раза в пять минут. На аккаунт хранится не больше 30 снимков и 16 MiB JSON снимков; реальные расходы базы с индексами и служебными данными выше. Старые избыточные снимки очищаются при следующем обновлении состояния.
- `Настройки` → `Помощь` включает в обезличенную диагностику размер последней записи и время сериализации/записи, без содержимого задач и секретов.

Проверки: `npm run test:audit-fixes`, `npm run test:task-editor`,
`npm run test:save-failures`. Они используют временные профили и искусственные
записи; Drive в audit-сценарии замокан. `npm run benchmark:state` измеряет
синтетическую обработку состояний со 100/1000/5000 задачами, а не задержку
production-сервера или браузерного диска.

### Ежедневные сценарии (0.34.10)

Подробная форма задачи показывает название и день работы; время, срок и детали
раскрываются независимо. В календарной сетке и таймлайне задача завершается
отдельной галочкой, а название открывает редактор. Сохранение закрывает форму
без остаточного затемнения; отказ записи сохраняет введённые данные.
Проверка в изолированном профиле: `npm run test:task-editor`.

Цели, заметки и доска используют компактные панели и цвета текущей темы,
сохраняя существующие действия и пользовательские цвета карточек.
Проверка тёмной/светлой темы и экранов 320–1440 px: `npm run test:workspace-panels`.

Архив использует компактный список по дням, фильтры и действия-иконки. Выбранные
записи подсвечиваются акцентом; видимые квадратные чекбоксы оформлены единообразно,
с поддержкой клавиатуры и частичного выбора. Высота содержимого не растягивает
верхний цветовой засвет. Изолированная проверка: `npm run test:archive`.

Настройки внешнего вида поддерживают восемь готовых акцентов и свой цвет через
палитру или HEX-код. Пользовательский цвет синхронизируется в аккаунте; оформление,
время и вложенные настройки визуально разделены. Проверка: `npm run test:appearance`.

Кнопки используют общий SVG-набор Lucide 1.52.0: единые контуры, значки меню,
закрытия и масштабирования. Лицензия: `app/assets/vendor/lucide.LICENSE.txt`.
Проверка символов и кнопок в отдельном профиле: `npm run test:icons`.
Проверка отката задач при отказе записи, восстановления перенесённых повторов
и вечерних интервалов календаря и таймлайна, архива и лимита подзадач: `npm run test:task-recovery`.

- Серия привычки сохраняется до конца незаконченного сегодняшнего дня. У числовых привычек показан основной шаг прибавления; он настраивается в форме и синхронизируется вместе с датированной конфигурацией.
- День календаря открывается около текущего времени, другие даты — около первого события. Увеличенное окно дня и недели не сжимается под шапкой; дела без времени и сроки находятся под сеткой. Занятия видны на таймлайне без повторного списка ниже. Нажатие и перенос учитывают четверти часа; в списках можно завершать задачи отдельной галочкой.
- Итоги статистики следуют выбранным 7/30/90 дням. Годовой heatmap остаётся отдельным представлением.
- «Новое ДЗ», «Новое занятие» и загрузка материала открывают компактные окна. Черновик ДЗ сохраняется при закрытии; несохранённые изменения предмета или занятия требуют подтверждения. Действия пары и задания собраны в меню.
- Раскрытая задача позволяет добавлять подзадачи по Enter и удалять отдельные пункты с отменой; после удаления последнего пункта весь блок исчезает. У повторов явно выбирается область изменения. «Незавершённые» поясняет, что показывает прошлые дни. Нижняя мобильная навигация использует иконки без сокращённых подписей.
- На телефоне доска по умолчанию показывает список карточек. Полотно доступно для редактирования; предпочтения мобильного и desktop-представления независимы. Акценты добавления следуют палитре.

Лишние разделы скрываются без удаления данных: `Настройки` → `Внешний вид` →
`Видимые разделы`, либо через настройку пространства «Учёба и дела».
Сохранённый пользователем выбор навигации автоматически не переписывается.

Изолированная проверка этих сценариев: `npm run test:daily-flow`.
Для проверки собранной веб-версии задайте `PARSITASKS_TEST_WEB=1`.

Трекер задач, привычек, целей и дневных записей на русском языке. Работает как PWA в браузере и как десктопное приложение на Electron. Данные хранятся local-first в `localStorage`, а после входа автоматически синхронизируются с общей приватной Postgres-БД в Supabase.

Веб-версия публикуется в Cloudflare Workers Static Assets. Старый автодеплой от
Git пока настраивается отдельно в Cloudflare; в 0.33.1 подготовлен защищённый путь
через GitHub Actions, выключенный до явного включения.

Каждый push и pull request проверяется Windows CI: зависимости, unit-тесты, lint,
пользовательские сценарии и сборки. Новый deploy job зависит от всех проверок и
публикует проверенный артефакт без пересборки. Пока старый Cloudflare-автодеплой
не отключён, он всё ещё может обходить этот барьер.
После публикации проверь точную ревизию и контрольные суммы ресурсов:

```powershell
npm run verify:production -- --revision FULL_COMMIT_SHA --wait 600
```

Локальный план подготовки к платному запуску и ограничения проверок:
`docs/COMMERCIAL_READINESS_2026-09-30.md`.

Включение защищённого выпуска, мониторинга, проверка артефактов и откат:
локальный документ `docs/RELEASE_OPERATIONS.md`. `npm run check:availability`
проверяет только публичные ресурсы, без входа и изменения личных данных.

В версии 0.32.1 проверены задержанные ответы при смене аккаунта, отказ локальной
записи, повреждённое состояние, обновление сессии и таймауты запросов.
Изолированная UI-проверка восстановления запускается через `npm run test:reliability`.
Она не использует личные аккаунты и не создаёт записи в production.

В версии 0.33.0 добавлены необязательная настройка пустого пространства и
`Настройки` → `Помощь`. Там можно повторно выбрать разделы, открыть диагностику
синхронизации и скачать обезличенный JSON для обращения. Файл содержит только
версию и состояние сохранения: без текстов записей, почты, адресов проектов и
секретов. Ничего не отправляется автоматически. Проверка первого запуска,
сохранения навигации, скачивания и мобильной доступности: `npm run test:onboarding`.

Тот же сценарий можно запустить на локальной веб-сборке в изолированном профиле
Chrome (нужен установленный Chrome и запущенный dev-сервер):

```powershell
$env:PARSITASKS_ONBOARDING_WEB_URL = "http://127.0.0.1:5193"
npm run test:onboarding
Remove-Item Env:\PARSITASKS_ONBOARDING_WEB_URL
```

Веб-сценарий отказывается открывать удалённые адреса и не использует браузерный
профиль пользователя.

Проверка компактных экранов и исправлений быстрого ввода:
`npm run test:ux-polish`. Нужен установленный Chrome, dev-сервер не нужен:
сценарий открывает локальные файлы в отдельном профиле, блокирует все HTTP-запросы
и проверяет отмену, сроки ДЗ и экраны 320/390/599/1440 px на искусственных данных.

Проверка стабильности переключателей календаря, акцентных палитр, компактной
плотности и создания подзадач: `npm run test:requested-polish`. Сценарий работает
без сети и личного аккаунта. Подзадачи — вложенные пункты родительской задачи:
добавляются через её меню, редактируются в форме задачи, не занимают отдельное
время календаря и не завершают родителя автоматически. Для повторов изменение
применяется только к выбранному выполнению либо к нему и будущим.

Регрессии сценарного аудита: `npm run test:audit`. Отдельный профиль Chrome,
сеть заблокирована; проверяются мобильное подтверждение, сведения незавершённых,
длинные названия, фильтры целей, отказ сохранения целей и массовый перенос
повторов с отменой, сохранением истории и двумя стратегиями переноса.
Локальные отчёт и статус исправлений: `docs/audits/2026-10-02-personas/REPORT.md`,
`docs/audits/2026-10-02-personas/FIXES.md`.

## Возможности

Ежедневный интерфейс сосредоточен на задачах, привычках и календаре. В форме
задачи сразу видны только название и день работы; категория, приоритет, время,
срок и повтор находятся в дополнительных настройках. Существующие данные не
удаляются. Включённые дополнительные разделы доступны через «Ещё», а мобильные
закрепления остаются настраиваемыми.

Календарь: «День / Неделя / Месяц / Статистика». День и неделя показывают
часовые блоки и учебные занятия; выбранный день раскрывается списком ниже.
Дела без времени и сроки сдачи не считаются занятыми часами. Можно создать
блок, перетащить задачу между днями или изменить его длительность. На телефоне
один палец прокручивает часы, два пальца меняют масштаб сетки, удержание задачи
позволяет перенести её с шагом 15 минут. Время под пальцами при масштабировании
остаётся на месте; масштаб сохраняется отдельно на устройстве. Обычный pinch
страницы на телефоне отключён, системные способы увеличения остаются доступны.
Нажатие открывает полное название и быстрые действия, а не сразу редактор.
Переключатель занятий и кнопки масштаба доступны в меню календаря.
Изолированная проверка реальными потоками touch-событий Chromium (не личный аккаунт):
`npm run test:calendar-touch`. Эмуляция не заменяет проверку на реальных Android/iOS.
В статистике доступны графики выполнения задач и привычек по расписанию
за 7, 30 или 90 дней: подсказки по датам, управление клавиатурой и таблица данных.
График задач показывает процент выполнения за день на шкале 0–100%; количество
видно в подсказке. Средний дневной процент не зависит от количества задач в день,
дни без задач исключены из расчёта.
Дни без обязательных привычек остаются пропусками, недельные цели учитываются
в итогах отдельно. Heatmap сохранён; проценты задач и привычек за период показаны
двумя открытыми карточками без обзора целей. В боковом меню доступен прогресс
выбранного дня. Отметка привычки
расположена слева от названия, как в задачах.
Изолированные проверки: `npm run test:minimal` и `npm run test:calendar-activity`.
Графики используют локальную сборку Chart.js без CDN; обновление: `npm run vendor:charts`.

не нужен: веб-сборка подставляет один хэш сборки в локальные скрипты и стили.

`app/src/nutrition/` содержит существующий экран питания. Этот перенос не
меняет его поведение.

## Удаленная БД

Parsitasks использует один общий Supabase-проект. Администратор один раз создаёт проект, выполняет `database/supabase-schema.sql` и задаёт публичный ключ в Cloudflare. После этого пользователю не нужны URL, ключи и собственная база:

1. Открыть отдельную страницу `/auth`.
2. Создать аккаунт по email, войти в существующий или продолжить через Google.
3. На остальных устройствах войти в тот же аккаунт.

Синхронизация включается автоматически после входа, сначала безопасно объединяет данные, затем сохраняет их в общую БД. Каждая строка и изображение изолированы по `auth.uid()` через RLS. При смене аккаунта приложение создаёт safety backup и не переносит локальные данные предыдущего аккаунта в новый.

Тема, акцентный цвет, плотность, формат времени, первый день недели, навигация и тихие часы сохраняются в `state.profile.preferences` той же приватной строки Supabase. Каждая настройка имеет собственную дату изменения: независимые офлайн-правки на разных устройствах объединяются, при конфликте одной настройки побеждает более поздняя. После первой загрузки облака прежние локальные настройки заполняют только отсутствующие значения. Новая таблица или SQL-миграция не нужны.

Разрешения и включение уведомлений на устройстве, расписание локальных резервных копий, реквизиты подключения, открытый экран, дата и фильтры остаются локальными. Изолированная проверка двух устройств без сети: `npm run test:settings-sync`.

Для локальной разработки без Worker технические поля Supabase остаются доступны. В web и desktop production-конфигурация загружается автоматически с `https://parsitasks.ru/api/public-config`.

### Вход через Google

1. В Google Auth Platform создай OAuth client типа `Web application`.
2. Добавь origin `https://parsitasks.ru` и Supabase callback `https://wvkiborhargrzsfwiliq.supabase.co/auth/v1/callback`.
3. В Supabase открой `Authentication` → `Providers` → `Google`, включи провайдер и укажи Client ID и Client Secret.
4. В `Authentication` → `URL Configuration` установи Site URL `https://parsitasks.ru` и добавь Redirect URL `https://parsitasks.ru/auth`. Для входа на локальном сайте добавь также точный Redirect URL `http://127.0.0.1:5185/auth` (или адрес и порт своего локального сервера).

Для локальной проверки отдельно добавь origin `http://127.0.0.1:8790` в Google и Redirect URL `http://127.0.0.1:8790/auth` в Supabase. В production локальные адреса лучше убрать.

### Синхронизация с Google Calendar

Интеграция использует отдельное согласие Google и не получает доступ к календарю при обычном входе. Refresh token хранится в Supabase только в зашифрованном виде.

1. В Google Cloud включи `Google Calendar API` для того же проекта.
2. В OAuth client типа `Web application` добавь redirect URI `https://parsitasks.ru/api/google-calendar/callback`.
3. Если OAuth consent screen находится в режиме Testing, добавь свой Google-аккаунт в `Test users`.
4. Снова выполни актуальный `database/supabase-schema.sql`, чтобы создать таблицу `google_calendar_connections` и её RLS-политики.
5. Добавь секреты в Cloudflare Worker:

```powershell
npx wrangler secret put GOOGLE_CALENDAR_CLIENT_ID
npx wrangler secret put GOOGLE_CALENDAR_CLIENT_SECRET
npx wrangler secret put GOOGLE_TOKEN_ENCRYPTION_KEY
```

Для `GOOGLE_TOKEN_ENCRYPTION_KEY` используй случайную строку длиной не меньше 32 символов. Например:

```powershell
$bytes = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[Convert]::ToBase64String($bytes)
```

После `git push` Cloudflare развернёт новую версию. Затем открой `Настройки` → `Google Calendar` → `Подключить Google Calendar`.

Режим `Parsitasks → Google` отправляет временные блоки в основной календарь. Режим `Двусторонняя` дополнительно импортирует обычные события Google как временные блоки Parsitasks. Синхронизируется период от 30 дней назад до 180 дней вперёд. Повторяющиеся задачи разворачиваются в независимые события на конкретные даты, поэтому исключение, перенос или удаление одного дня не изменяет остальные экземпляры серии.

### Учёба и Google Drive

В разделе «Учёба» предметы и занятия хранятся в том же local-first состоянии, что и другие данные Parsitasks. Домашнее задание — обычная задача с привязкой к предмету: выполнение, дедлайн и напоминание видны также в основном списке. Выполненное ДЗ остаётся в панели «Учёба» до конца даты сдачи, затем скрывается только из этой панели; задачу по-прежнему можно открыть в основном списке за прошлую дату. При выборе предмета форма предлагает дату следующей практики, а если её нет — следующей лекции; дату можно изменить. В «Материалах» файлы загружаются в папку `Parsitasks` **личного Google Drive подключившегося пользователя**. В Supabase и JSON-экспорте сохраняются только метаданные и ID файлов, не их содержимое. Удаление материала из Parsitasks не удаляет его из Drive.

В расписании можно задать опорный понедельник и указать, чётная это неделя или нечётная. Цикл чередуется каждые семь дней, включая переход через новый год. Каждое занятие назначается на все, только чётные или только нечётные недели; старые занятия остаются еженедельными. Стрелки переключают просматриваемый день или неделю. Подсказка дедлайна учитывает цикл и тип занятия.

Каждый аккаунт Parsitasks подключает свой Google-аккаунт отдельно. Для подключения используется минимальный scope `drive.file`, отдельный от Google Calendar; refresh-токен хранится зашифрованным в `google_drive_connections` с RLS по `user_id`. Крупные файлы загружаются через возобновляемую сессию небольшими фрагментами. Десктопная версия открывает веб-версию для первоначального согласия Google; после подключения файлы доступны в обоих приложениях через тот же аккаунт Parsitasks.

Настройка для production:

1. В Google Cloud включи `Google Drive API` и добавь scope `https://www.googleapis.com/auth/drive.file` на OAuth consent screen. Используй тот же OAuth client типа `Web application`, что и для Google Calendar.
2. Добавь разрешённый redirect URI `https://parsitasks.ru/api/google-drive/callback`. Для локальной проверки Worker добавь соответствующий `http://127.0.0.1:<port>/api/google-drive/callback`.
3. Переведи OAuth consent screen из режима `Testing` в `Production` и пройди требуемую Google проверку для внешних пользователей. В режиме `Testing` подключаться могут только test users, а refresh-токены для этого scope истекают через 7 дней.
4. Снова выполни `database/supabase-schema.sql` в Supabase SQL Editor. Это добавит таблицу `google_drive_connections` и политики RLS, не удаляя текущие данные.
5. Проверь, что в Cloudflare заданы `GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET` и `GOOGLE_TOKEN_ENCRYPTION_KEY`. Drive использует тот же OAuth client, но выдаёт отдельное согласие. После деплоя подключи диск через «Учёба» → «Подключить Drive».

Для локального Worker скопируй `.dev.vars.example` в `.dev.vars` и заполни публичный ключ Supabase, Client ID, Client Secret и ключ шифрования. `.dev.vars` не коммить: локальный Wrangler не получает секреты Cloudflare автоматически. Добавь в Google OAuth client ещё один redirect URI `http://127.0.0.1:5185/api/google-drive/callback` и перезапусти локальный Worker. Вход в Parsitasks через Google и подключение Drive — разные согласия; настройка первого не включает второе автоматически.

Отзыв доступа к Drive, удаление файла в самом Drive или смена Google-аккаунта могут сделать старые ссылки недоступными. JSON-экспорт не является резервной копией бинарных файлов: их нужно сохранять средствами Google Drive. Пока поддерживается загрузка новых файлов; выбор уже существующих файлов через Google Picker остаётся отдельной задачей.

После обновления до `0.17.1` выполни актуальный `database/supabase-schema.sql` ещё раз. Он добавит историю последних 30 облачных версий, краткую сводку для каждой версии и защищённое удаление собственного аккаунта; существующие задачи и аккаунт при этом сохранятся.

После обновления до `0.18.0` повторно выполни `database/supabase-schema.sql`, чтобы в краткой сводке новых облачных версий отображалось количество записей дневника. Сами записи синхронизируются и без этого обновления схемы.

После обновления до `0.20.0` снова выполни актуальный `database/supabase-schema.sql`, чтобы сводка облачных версий показывала количество блюд. Сам план питания синхронизируется и без повторного выполнения схемы.

После обновления до `0.22.1` снова выполни актуальный `database/supabase-schema.sql`. Он создаст приватное хранилище `board-images` и RLS-политики для изображений доски. Новое изображение сначала загружается в Supabase Storage и только после успешной загрузки появляется на доске; IndexedDB используется лишь как локальный кеш для быстрого отображения. Обычный JSON-экспорт сохраняет структуру доски и пути к файлам, но не дублирует бинарные изображения.

После обновления до `0.24.0` обязательно снова выполни `database/supabase-schema.sql`. Миграция привязывает legacy `user_key` к ID владельца, отзывает лишние права `anon`/`authenticated` и закрывает прямой вызов служебных trigger-функций.

### Live-проверка Supabase

Обычные тесты не обращаются к сети. Для проверки настоящих Supabase Auth, таблицы `rhythm_states` и RLS задай переменные окружения тестового аккаунта и выполни:

```powershell
$env:RHYTHM_SUPABASE_URL = "https://project.supabase.co"
$env:RHYTHM_SUPABASE_ANON_KEY = "публичный anon key"
$env:RHYTHM_SUPABASE_EMAIL = "test@example.com"
$env:RHYTHM_SUPABASE_PASSWORD = "пароль тестового аккаунта"
$env:PARSITASKS_LIVE_TEST_ACCOUNTS = "1" # Только после выбора отдельного тестового аккаунта
npm run test:sync-live
```

Проверка выполняет вход и чтение доступной пользователю строки. Она не создаёт и не перезаписывает задачи.

Личные аккаунты не используются. Без `PARSITASKS_LIVE_TEST_ACCOUNTS=1` оба
live-сценария завершаются до входа и обращения к данным. Для проверки RLS нужны
два временных аккаунта из `.security-test.env.example`; после их настройки и
создания контрольной записи только в тестовом пространстве запускается
`npm run test:security-live`. Проверка RLS делает пробные запросы записи и
хранилища; это не сценарий для личного рабочего пространства.

Для тестового аккаунта, в котором уже есть облачное сохранение, можно дополнительно проверить запись и конфликт версий. Содержимое состояния при этом не меняется:

```powershell
$env:RHYTHM_SYNC_LIVE_WRITE = "1"
npm run test:sync-live
```

Сессия аккаунта хранится отдельно на устройстве и не попадает в JSON-экспорт или удаленный `ui_state`. Доступ к данным разрешён только вошедшему пользователю через Supabase Auth и RLS.

`Загрузить из БД` заменяет локальное состояние удаленным, но перед этим создает safety backup.

## Подключение ChatGPT через MCP

MCP работает на `https://parsitasks.ru/mcp` внутри того же Cloudflare Worker. Он позволяет ChatGPT:

- получать обзор задач, привычек и целей;
- читать запись дневника за день или период и безопасно дописывать новый абзац;
- составлять недельное резюме дневника по запросу пользователя;
- читать план питания, продукты, цели и список покупок;
- создавать, менять, переносить, отмечать и удалять блюда, а также сохранять продукты и шаблоны;
- приостанавливать и возобновлять план без удаления данных;
- предварительно проверять и затем атомарно применять полный план питания на неделю с одним Undo;
- искать и открывать отдельные записи;
- создавать задачи без дублей при повторном запросе;
- отмечать конкретный день задачи выполненным или возвращать его в работу;
- переносить и редактировать задачи, включая безопасное разделение повторяющихся серий;
- отмечать чек-привычки и числовые значения;
- создавать цели и управлять их чекпоинтами;
- получать данные для утреннего плана и вечернего итога;
- просматривать журнал действий и отменять изменения.
- получать календарь за период до 93 дней, список накопившихся задач и статистику продуктивности;
- создавать, переименовывать, приостанавливать и возвращать привычки без изменения их прошлой истории;
- изменять и удалять цели, дублировать отдельную задачу или серию и скрывать просмотренные просрочки;
- просматривать, создавать, переименовывать и безопасно удалять категории с переносом задач в заменяющую категорию.
- предварительно проверять пакет переносов, а затем применять весь план одним обратимым действием;
- создавать задачи с повтором по выбранным дням, числу месяца или интервалу.

Доступ ChatGPT к чтению и записи дневника настраивается независимо в разделе `Настройки` → `ChatGPT`. Удаление через MCP требует явного подтверждения. Для повторяющейся задачи ChatGPT обязан уточнить область: один день, этот и последующие или вся серия. Каждый запрос выполняется от имени вошедшего пользователя через Supabase Auth и RLS. Запись использует проверку `updated_at`, поэтому параллельное изменение с другого устройства не затирается. Worker ограничивает резкие всплески запросов, а последние 100 действий хранятся в синхронизируемом журнале.

### 1. Настроить Cloudflare

В Cloudflare открой Worker `tasks-and-habits` → `Settings` → `Variables and Secrets` и добавь переменную:

```text
SUPABASE_PUBLISHABLE_KEY=публичный sb_publishable_... key проекта Supabase
```

`SUPABASE_URL`, основной адрес сайта и часовой пояс уже заданы в `wrangler.jsonc`. Legacy `SUPABASE_ANON_KEY` пока поддерживается, но Supabase выводит старые anon-ключи из употребления. `sb_secret_...` и `service_role` использовать здесь нельзя: Worker специально откажется публиковать такой ключ.

Полный production-чеклист находится в `SECURITY.md`.

Для локального запуска скопируй `.dev.vars.example` в `.dev.vars`, впиши ключ и выполни:

```powershell
npm run mcp:dev
```

### 2. Включить OAuth в Supabase

1. Открой `Authentication` → `OAuth Server`.
2. Включи OAuth 2.1 Server.
3. Укажи Authorization Path: `/oauth/consent`.
4. Включи Dynamic Client Registration.
5. В `Authentication` → `URL Configuration` укажи Site URL: `https://parsitasks.ru`.
6. Рекомендуется использовать асимметричный JWT signing key `RS256` или `ES256`.

После деплоя проверь:

```text
https://parsitasks.ru/mcp/health
https://parsitasks.ru/.well-known/oauth-protected-resource
```

Первый адрес должен вернуть `ok: true`, второй — OAuth metadata с Supabase authorization server.

### 3. Добавить приложение в ChatGPT

1. В ChatGPT открой `Settings` → `Security and login` и включи Developer mode.
2. Открой `Settings` → `Plugins`.
3. Нажми `+` и создай developer-mode app.
4. Название: `Parsitasks`.
5. MCP server URL: `https://parsitasks.ru/mcp`.
6. При первом запросе войди в Parsitasks и нажми `Разрешить` на экране согласия.

Примеры запросов:

```text
Что у меня сегодня?
Найди мои задачи по SQL.
Создай завтра в 14:00 задачу «Позвонить врачу» с высоким приоритетом.
Отметь сегодняшнее выполнение задачи «Решить задачи SQL» завершенным.
```

## Публикация сайта

Cloudflare Workers подключается к приватному GitHub-репозиторию и автоматически публикует каждый push в `master`. Параметры проекта:

- production branch: `master`;
- build command: `npm run build:cloudflare`;
- deploy command: `npx wrangler deploy`;
- root directory: оставить пустой;
- static assets directory задается в `wrangler.jsonc` как `web-dist`.

Команда публикации сначала запускает unit-тесты и lint, затем собирает чистый статический каталог `web-dist`. Для корректных ссылок подтверждения email полученный адрес `*.workers.dev` нужно указать в Supabase в `Authentication` → `URL Configuration` как `Site URL` и добавить в `Redirect URLs`.


### Публикация десктоп-релиза

Версия в `package.json` и Git-тег должны совпадать. После готового коммита достаточно отправить тег:

```powershell
$version = (Get-Content package.json | ConvertFrom-Json).version
git tag "v$version"
git push origin "v$version"
```

Workflow `Desktop Release` запускает тесты на Windows, собирает обе версии и публикует их в GitHub Releases вместе с `latest.yml`. Установленное приложение проверяет этот файл после запуска и затем каждые четыре часа, загружает новую версию в фоне и предлагает перезапуск.

Windows-сборка пока не подписана коммерческим сертификатом, поэтому при первой установке SmartScreen может показать предупреждение. Для уже установленного приложения это не отключает механизм обновлений.

Готовые файлы появятся в папке `dist`.

## О миграции на фреймворк

Перенести приложение на фреймворк можно. Самый разумный путь — не переписывать все сразу, а сначала отделять чистую бизнес-логику от DOM. Первый шаг уже сделан: быстрый ввод, переносы задач и toast вынесены из `app.js`.

Если делать полноценную миграцию, хорошие варианты:

- React + Vite — лучший выбор, если нужен компонентный интерфейс, тесты и дальнейший рост.
- Svelte + Vite — проще и легче для небольшого локального приложения.
- Vue + Vite — тоже хороший вариант, если нравится декларативный шаблонный стиль.

Для этого проекта оптимален React + Vite: бизнес-логика уже вынесена в независимые модули и может использоваться без переписывания. Миграцию стоит вести по экранам: сначала оболочка и настройки, затем цели и привычки, после них задачи и календарь, а сложный timeline переносить последним. Формат локальных и облачных данных при этом останется прежним.
