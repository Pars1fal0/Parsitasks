Проверен коммит `b509928378dd1331b01ecbc6343393c36a45c178` (`0.36.1`), клонированный в `D:\parsitasks`. Среда: Windows, Node.js 24.11.1, npm 11.6.2.

## 1. P1 — отмена MCP-действия стирает последующие изменения

Код: `mcp/activity-service.mjs:9`, `mcp/activity-service.mjs:130`, `mcp/write-service.mjs:60`, `mcp/journal-service.mjs:62`. Аналогичное применение отмены в интерфейсе: `app/src/integrations/mcp-activity.js:55`.

`recordMcpActivity()` создаёт проверки ожидаемого состояния сущностей только при `details.guard === true`. Несколько существующих команд, включая `updateTaskCommand()` и `appendJournalEntryCommand()`, этот флаг не передают. Поэтому при отмене сохранённая старая сущность целиком заменяет актуальную, а отсутствие `expected` трактуется как отсутствие необходимости проверять конфликт.

Воспроизведение:

1. Изменить название задачи через MCP.
2. После этого отметить её выполненной.
3. Отменить первое MCP-действие: отметка выполнения исчезает. Проверено и через серверный `undoMcpCommand()`, и через клиентский `undoActivity()`.
4. Аналогично: дополнить существующий дневник через MCP, затем вручную дописать текст, затем отменить MCP-дополнение. Более поздний пользовательский текст исчезает из записи.

Ожидается сохранение последующих правок либо явный отказ от конфликтующей отмены. Нужна единая политика проверки конфликтов для всех производителей inverse-patch. Для уже сохранённых действий без `expected` нужен безопасный режим, а не безусловное восстановление сущности. Существующие резервные копии не гарантируют сохранение каждой промежуточной правки.

## 2. P1 — лимит календарной синхронизации превращается в удаление действительных событий Google

Код: `app/src/integrations/google-calendar-occurrences.js:18`, `mcp/google-calendar.mjs:268`.

`buildCalendarTasks()` сначала обрезает развёрнутые задачи до 1000, затем строит `activeIds` по обрезанному списку. Ранее связанные задачи, которые не поместились в пакет, попадают в `staleTaskIds`. Клиент отправляет их как `outOfRangeTaskIds`, а сервер выполняет `DELETE` соответствующих событий в Google Calendar.

Воспроизведение: 1001 действительная задача с временем внутри выбранного диапазона; последняя уже связана с Google. Получено `tasks.length = 1000`, `skipped = 1`, `staleTaskIds = ['task-1000']`. Вызов настоящего серверного обработчика с подставным Google API произвёл `DELETE /calendar/v3/calendars/primary/events/event-1000`, хотя задача существует и находится внутри диапазона.

Порог достижим и при небольшом количестве ежедневных серий: лимит применяется к их развёрнутым повторениям за несколько месяцев. Следует вычислять существующие повторения до ограничения пакета и отделить пропуск из-за лимита от намеренного удаления. Для крупных календарей нужна порционная синхронизация или явное сообщение о частичном результате.

## 3. P2 — ответы Google Calendar API не доступны desktop-клиенту из-за CORS

Код: `mcp/worker.mjs:67`, `mcp/google-calendar.mjs:663`, `app/src/integrations/google-calendar-api.js:18`.

Desktop загружается из `file:` и обращается к `https://parsitasks.ru/api/google-calendar/...`. Worker возвращает обработчик Calendar напрямую. CORS-заголовок добавляется к ответам Drive, но не Calendar. Успешный preflight не заменяет CORS-заголовок на основном ответе.

Проверка с синтетическим авторизованным запросом `/api/google-calendar/status` и `Origin: null` получила HTTP 200 без `Access-Control-Allow-Origin`. Стандартный renderer Electron с включённой web security не сможет прочитать такой ответ. Это мешает получению статуса и синхронизации Calendar в desktop, даже если подключение было настроено в веб-версии.

Нужно согласовать CORS на основных ответах, ошибках и OPTIONS для поддерживаемого desktop-origin. Отдельная проверка должна выполнять настоящий cross-origin fetch из изолированного renderer, а не только мокать `fetch` в unit-тесте.

## 4. P2 — desktop блокирует ссылки на учебные материалы и OAuth Google Calendar

Код: `desktop/main.cjs:77`, `desktop/main.cjs:252`, `app/src/study/study-controller.js:405`, `app/src/study/study-controller.js:548`, `app/src/integrations/google-calendar-controller.js:68`.

Обработчик новых окон всегда возвращает `deny`, а системный браузер открывает только для `github.com`, `parsitasks.ru` и `www.parsitasks.ru`. При этом материалы учёбы открываются ссылками `https://drive.google.com/file/d/.../view`, а Calendar в desktop вызывает `open()` для `https://accounts.google.com/...`.

Проверка фактической функции `isAllowedExternalUrl()` подтвердила, что оба Google-адреса отклоняются. Ссылки на материалы не открываются; попытка подключения Calendar также блокируется. Разрешения CORS из пункта 3 сами по себе этот дефект не устранят.

Для материалов нужен проверенный набор поддерживаемых HTTPS-адресов Google. Для Calendar предпочтителен согласованный переход в веб-версию для подключения, как уже сделано для Drive: OAuth также зависит от cookie состояния, которую текущий desktop-fetch не переносит в системный браузер автоматически.

## Зависимости

`npm audit --json` обнаружил одну уязвимость **moderate**, high/critical — 0. Установлен `ip-address@10.7.2`, цепочка: `@modelcontextprotocol/sdk → express-rate-limit → ip-address`; в lock-файле пакет отмечен как dev-зависимость. Это не подтверждает доступность уязвимого кода из опубликованного Worker.

Согласно [GHSA-rxp7-6hxx-x8q5](https://github.com/advisories/GHSA-rxp7-6hxx-x8q5), затронуты версии до 10.7.3 включительно; исправление — 10.7.4. Специальная IPv6-строка может вызвать длительную синхронную обработку. Рекомендуется обновить разрешение зависимости в lock-файле и повторить audit/сборку. Эксплуатация против production не выполнялась.
