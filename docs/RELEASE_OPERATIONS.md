# Выпуск и контроль доступности

## Текущее состояние

Новый путь выпуска подготовлен в коде, но по умолчанию выключен. Пока в
Cloudflare действует отдельный автодеплой от Git, он может обходить GitHub CI.
Добавление workflow само по себе не меняет настройки Cloudflare и не закрывает
этот обход. Не включайте два активных пути публикации одновременно.

Этот этап не создаёт пользователей, не меняет данные аккаунтов, не включает
платные услуги и не публикует Windows portable.

## Как включить защищённый путь

1. Cloudflare → Workers & Pages → `tasks-and-habits` → Settings → Builds:
   отключите автоматические production-деплои. Можно отключить подключённые
   Builds или заменить deploy command на `npx wrangler versions upload`, чтобы
   сборки создавали версии без продвижения в production. Сначала проверьте, что
   прежний путь действительно больше не активирует версии.
2. Создайте ограниченный Cloudflare API token для нужного аккаунта и Worker.
   В GitHub → Settings → Environments создайте `production`; добавьте секреты
   `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`. Не используйте глобальный API
   key и не добавляйте Supabase service-role или личные OAuth-токены.
3. Ограничьте environment веткой `master`. Если тариф GitHub поддерживает
   обязательное подтверждение, добавьте required reviewer. Для ветки включите
   обязательный успешный job `verify`, запрет обхода и force push.
4. Проверьте `Application Verification` на актуальном коммите. Он запускает
   unit, UI, восстановление, onboarding и smoke, собирает Worker и сайт, затем
   сохраняет готовый артефакт на 14 дней.
5. Только после выполнения предыдущих пунктов задайте repository variable
   `PARSITASKS_GATED_DEPLOY_ENABLED=1`. Запустите `Application Verification` на
   `master` через Actions или следующим согласованным push.

Deploy job зависит от успешного `verify`, не работает для pull request и других
веток, использует артефакт этого же прогона без пересборки. Контрольные суммы всех
файлов и контрольная сумма их списка передаются отдельно через output проверяющего
job. Любая подмена файла или самого списка останавливает выпуск. Проверяются
полный Git SHA, отсутствие незакоммиченных изменений и актуальность `master`.
После публикации проверяются страницы и все публичные файлы нужной ревизии.

Секреты Cloudflare доступны только шагу публикации. Google/Supabase-секреты не
копируются в артефакт; `keep_vars` сохраняет серверные переменные из панели.
Без настройки environment и отключения старого пути защита выпуска не считается
включённой. Реальный прогон GitHub Actions и откат нужно проверить отдельно.

Официальные инструкции: [Cloudflare Builds](https://developers.cloudflare.com/workers/ci-cd/builds/),
[GitHub Actions для Workers](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/),
[артефакты GitHub Actions](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts).

## Локальная проверка артефакта

```powershell
npm run build:web
npm run build:worker
npm run release:prepare
npm run release:verify -- --revision FULL_COMMIT_SHA
npx --no-install wrangler deploy --config .release-candidate/wrangler.json --no-bundle --dry-run
```

`release:prepare` требует чистую рабочую директорию. Для проверки локальных
незакоммиченных правок можно добавить `-- --allow-dirty` к prepare и verify.
Получившийся артефакт помечен `sourceDirty=true`; обычная проверка выпуска его
отклонит. Не публикуйте такую сборку. Не переносите флаг `--allow-dirty` в CI.

При работе локального Wrangler сначала остановите именно свой dev-сервер: на
Windows он может удерживать файлы `web-dist`. Не закрывайте чужие процессы.

## Публичный мониторинг

```powershell
npm run check:availability
npm run check:availability -- --full
```

Лёгкая проверка делает семь анонимных HEAD/GET-запросов: главная, вход, приложение,
манифест релиза, публичная конфигурация, health и отказ MCP неавторизованному
клиенту. Проверяются статус, заголовки защиты, версия и настройка авторизации.
Личные данные, вход в аккаунт, тестовые задачи и запросы записи не используются.
Таймаут покрывает также чтение ответа; размер JSON ограничен.

`--full` дополнительно сверяет контрольные суммы всех публичных файлов. Это не
проверка реальной изоляции Supabase, доставки почты, Google OAuth или Web Push.

Для включения `Public Availability` задайте repository variable
`PARSITASKS_MONITORING_ENABLED=1`. Workflow можно запустить вручную; расписание —
раз в час. Без этой переменной job пропускается. Уведомления об ошибках требуют
настроенных уведомлений GitHub Actions; отдельный контакт поддержки не придуман.
Расписание GitHub может задерживаться и не является гарантированным SLA.
В приватном репозитории расходуются CI-минуты: учтите около 720 запусков в месяц
плюс основные проверки перед включением. Никакие внешние платные сервисы не
подключаются автоматически.

## Ошибки и приватность

Обработчик Worker и Google OAuth callbacks пишут только событие, случайный
`requestId`, постоянную группу маршрута, метод и статус. Исходное исключение,
полный URL, OAuth code, заголовки, почта, токены и содержимое запроса не записываются
этими обработчиками. Клиент получает `X-Request-ID` для поиска события.

Это не гарантия обезличивания всех платформенных логов. В Cloudflare отдельно
нужно проверить invocation logs, tracing, сроки хранения, доступ и квоты; эти
настройки на данном этапе не менялись. Не включайте логирование полных URL с
OAuth-кодами и тел запросов.

## Откат

Если проверка после публикации упала, выпуск считается неуспешным, но предыдущая
версия не активируется автоматически: нельзя молча откатывать данные или
несовместимую миграцию. В Cloudflare выберите последнюю известную рабочую версию
Worker, выполните согласованный откат и повторите `check:availability` и
`verify:production` с Git SHA восстановленной версии.

Смена версии Worker не откатывает Supabase и файлы Drive. Перед SQL-миграциями
нужны копия базы, план совместимости и отдельная проверка восстановления на
тестовом окружении. Сохранённый GitHub-артефакт также не является резервной копией
пользовательских данных.
