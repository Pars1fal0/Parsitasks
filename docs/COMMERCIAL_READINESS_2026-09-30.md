# Parsitasks: подготовка к коммерческому использованию

Обновлено: 1 октября 2026. Текущий этап: контроль выпуска и публичный мониторинг, версия 0.33.1; включает первый запуск 0.33.0 и надёжность 0.32.1. Первоначальный отчёт: 30 сентября, версия 0.28.0.

## Вывод

Приложение подходит для дальнейшего закрытого бета-тестирования. Наличие большого числа функций и автоматических тестов пока не означает готовность к платному запуску. Главный приоритет сейчас: доверие к сохранению, синхронизации и восстановлению данных, затем понятная помощь и управление аккаунтом.

## Проверено и исправлено в 0.32.1

- Устаревшие ответы синхронизации не объединяются с другим аккаунтом; сброс очереди инвалидирует уже выполняющийся запрос.
- Облачные версии, восстановление и подтверждение удаления привязаны к аккаунту, открывшему действие. Эти проверки выполнялись на имитации API, не на личном аккаунте.
- Пока выбранный аккаунт ещё загружается, отправка локального пространства предыдущего пользователя заблокирована.
- Объединённые данные сначала записываются локально, затем продвигается облачная ревизия. При отказе записи состояние откатывается, очередь изменений не объявляется отправленной.
- Ручное объединение ставится в очередь отправки. Замена из облака не затирает локальную правку, сделанную за время подтверждения.
- Запросы входа и синхронизации ограничены 30 секундами, включая чтение ответа. Повторная попытка остаётся доступна после таймаута.
- Параллельные обновления сессии используют один запрос; ошибка 5xx не удаляет сессию. Поздние ответы не возобновляют вышедший аккаунт и не заменяют новый.
- Локальное восстановление откатывается при заполненном хранилище. Валидный JSON с неправильной структурой не превращается молча в пустое пространство; используется корректная резервная копия.
- Сообщения различают частичный успех: восстановление облака, запись на устройстве и загрузку списка версий.
- Отдельные учебные коллекции принимаются импортом, повреждённые отклоняются. Описана граница JSON-копии: ссылки не содержат сами файлы Drive и изображения доски.
- Добавлены 22 проверки отказов и гонок, а также Electron-сценарий восстановления при заполненном хранилище и после повреждения JSON. Профиль изолированный, внешние облачные записи не создавались.

## Первый опыт и помощь в 0.33.0

- Для пустого пространства добавлено пропускаемое предложение настройки. Нет обязательного модального окна, демонстрационных задач и принудительного подключения интеграций.
- Наборы «Задачи и привычки» и «Учёба и дела» меняют только навигацию по явному выбору. Текущие разделы можно оставить без изменений; закрытие окна не применяет выбор.
- Отметка настройки хранится отдельно для каждого аккаунта на устройстве. Уже заполненное пространство не получает предложение первого запуска.
- В настройках есть «Помощь» и переходы к настройке разделов и диагностике синхронизации.
- Обезличенный отчёт доступен для просмотра и скачивания. Его поля ограничены явным списком; задачи, заметки, почта, ключи, токены, адреса проектов и произвольный текст ошибок исключены. Автоматической отправки нет.
- Отказ локальной записи не сбрасывает навигацию и не закрывает форму настройки.
- Live-сценарии требуют отдельного явного флага выбора временных аккаунтов; создание доказательной задачи выключено в примере по умолчанию. Настоящие облачные аккаунты на этом этапе не проверялись.
- Проверены 411 unit-тестов, полный набор UI-сценариев, восстановление, планирование и desktop smoke. Новый сценарий настройки и реального скачивания диагностики прошёл в Electron и Chrome на отдельном пустом профиле, включая доступность на 320/390/1440 px. Web и Worker dry-run собраны без публикации.

### Границы текущей проверки

- Автоматические проверки и имитация задержек не подтверждают изоляцию реального Supabase. Нужны два специально созданных тестовых аккаунта и разрешение на облачные тестовые записи.
- Настройки CAPTCHA, почты, резервных копий провайдера, квот и Google OAuth в панелях production не проверялись и не менялись.
- Не проводились нагрузочные испытания на платных ресурсах и реальное восстановление инфраструктуры из копии провайдера.
- Питание не развивалось, Windows portable не пересобирался. Версия 0.33.1 подготовлена локально; этот этап сам по себе не публикует её.

## Контроль выпуска в 0.33.1

- Подготовлен deploy job с зависимостью от полного Windows CI и публикацией именно проверенного артефакта, без повторной сборки. Git SHA, все файлы и независимая контрольная сумма манифеста проверяются перед деплоем.
- Грязная рабочая директория допускается только для локального dry-run; обычная проверка выпуска её отвергает. GitHub проверяет актуальность ветки перед публикацией.
- Новый путь требует явного включения и environment `production`. Старый автодеплой Cloudflare нужно отключить отдельно: код workflow не меняет настройки провайдера. Реальная защита выпуска пока не включена и не проверена в GitHub.
- Реализован выключенный по умолчанию часовой мониторинг только публичных ресурсов. Проверка вручную подтвердила доступность production 0.32.0 без входа в аккаунт и пользовательских записей.
- Основной обработчик Worker и OAuth callbacks больше не записывают исходные исключения и URL; оставляют только непрозрачный идентификатор и постоянные поля события. Настройки платформенных логов и хранения отдельно не проверены.
- Подготовлена [инструкция включения и отката](RELEASE_OPERATIONS.md). Автоматический откат данных, платежи и платный мониторинг не добавлялись.
- Проверены 424 unit-теста, lint и аудит зависимостей; пройдены сценарии восстановления и первого запуска в изолированном профиле. Web, Worker и запечатанный выпускной артефакт собраны в dry-run без публикации; обычная проверка отвергла артефакт из незакоммиченной рабочей директории.
- Полная публичная проверка production 0.32.0 подтвердила 123 файла сборки, маршруты и защитные заголовки. Это проверка доступности опубликованной версии, не проверка пользовательских данных или реального нового CI-деплоя.

## История: этап 0.28.0

- Действия в питании больше не сообщают об успехе, если локальное хранилище отказало. Создание, изменение, удаление, перенос, копирование, смена статуса и настройка целей возвращают реальный результат сохранения.
- При отказе откатываются не только блюда, продукты и рецепты, но и метаданные синхронизации и отметки удаления. Введённый продукт и значения целей остаются в форме для повторной попытки.
- Удаление после подтверждения не применяется к старому состоянию, если рабочее пространство успело смениться.
- Копия съеденного блюда становится запланированным блюдом, а не автоматически съеденным.
- Очистка метаданных синхронизации сохраняет информацию об изменениях продуктов, блюд и рецептов. Раньше эти коллекции отсутствовали в списке живых сущностей.
- Обновлены зависимости в пределах существующих основных версий. Аудит установленного дерева больше не находит известных уязвимостей. Это проверка известных advisories, а не доказательство отсутствия всех уязвимостей.
- Добавлена Windows CI-проверка каждого push в master и pull request: установка по lock-файлу, аудит зависимостей, unit-тесты, lint, пользовательские Electron-сценарии, веб-сборка и Worker dry-run. Actions закреплены на Git SHA, права ограничены чтением.
- Cloudflare-сборка дополнительно требует успешного аудита, unit-тестов и lint. Windows UI-проверка пока идёт параллельно и сама по себе не блокирует автоматическую публикацию.
- Веб-сборка публикует release.json с версией, Git SHA и контрольными суммами публичных ресурсов. Проверка прода сверяет все ресурсы, основные страницы, заголовки защиты и отказ MCP анонимному клиенту. Секреты и пользовательские данные в манифест не входят.

Вместе с этим этапом выпускаются ранее подготовленные проценты календаря, счётчики в годовых подсказках, настраиваемая навигация, тихие часы, откладывание напоминаний и библиотека блюд.

## Что ещё мешает пользователю

1. **Нужна проверка полного цикла управления аккаунтом на тестовом облаке.** Удаление аккаунта и облачных данных с повторным подтверждением уже реализовано. Осталось проверить очистку интеграций и сроки хранения копий у провайдера; локальные копии и файлы Drive отдельно пояснить пользователю.
2. **Не определён канал поддержки.** Помощь и просмотр безопасной диагностики реализованы. Осталось выбрать реальный контакт, сроки ответа и способ передачи файла; нельзя подставлять вымышленную почту или автоматически отправлять данные.
3. **Первый опыт нужно проверить с новыми пользователями.** Пропускаемая настройка разделов реализована без принуждения к заполнению всех модулей. Нужна обратная связь людей, впервые открывших приложение, а не только автоматические сценарии.
4. **Веб-напоминания зависят от открытого приложения.** Тихие часы и откладывание не делают уведомления серверными. Для надёжного закрытого браузера нужен отдельный Web Push-проект с разрешением пользователя, отменой подписки и защитой от повторов.
5. **Доверие к синхронизации нужно проверять на реальных аккаунтах.** Локальные тесты не заменяют испытания двух устройств, потери сети, истечения сессии и конфликтующих изменений на действующем облаке.

## Следующие этапы

### P0: до платного запуска

- Проверить RLS и приватное хранилище двумя отдельными тестовыми аккаунтами. В репозитории есть live security-тест, но в этом этапе нет настроенных тестовых учётных данных; облачная изоляция не подтверждена этим прогоном.
- Проверить настройки провайдера: ограничения регистрации и восстановления пароля, CAPTCHA, защиту паролей, почтовую доставку, квоты и оповещения. Наличие этих настроек в прод не следует предполагать без доступа к панели.
- Проверить уже реализованное удаление аккаунта и данных на отдельном тестовом аккаунте, включая очистку интеграций; не использовать личный аккаунт для проверки.
- Включить и проверить подготовленный публичный мониторинг; отдельно определить мониторинг синхронизации, контакты поддержки и процесс реагирования. Публичный health не заменяет реальные проверки облака.
- Включить подготовленный блокирующий выпускной процесс, отключить старый Cloudflare-автодеплой, настроить защиту ветки и проверить ручной откат. До этого CI и старый автодеплой могут идти параллельно. Перед миграциями нужны резервная копия и проверка восстановления.
- Проверить юридические требования к конкретному оператору, рынкам и способам оплаты. Политику хранения, условия и согласия нельзя честно составить без этих исходных данных.

### P1: качество первого опыта

- Проверить реализованную настройку первого запуска с новыми пользователями.
- Определить реальный контакт поддержки и процесс обработки обезличенной диагностики; помощь и пакет диагностики реализованы.
- Проверки пределов localStorage на больших рабочих пространствах; оценить IndexedDB и миграцию только после измерений. Нынешний откат предотвращает ложный успех, но не увеличивает доступное место.
- Протестировать восстановление после повреждённого импорта и конфликтов на двух реальных устройствах.
- Подписать Windows-сборки сертификатом перед широким распространением. Веб-публикация не является выпуском подписанного установщика.

### P2: после стабильной беты

- Надёжные Web Push-напоминания.
- Тарифы и лимиты, основанные на реальной стоимости облака; платежи с идемпотентными webhook и проверкой доступа на сервере.
- Расширять функции по обратной связи и измерениям использования, а не добавлять ещё один универсальный раздел.

## Как проверять выпуск

Локально: npm ci, npm run test:dependencies, npm test, npm run lint, npm run test:e2e, npm run test:planning, npm run test:reliability, npm run test:onboarding, npm run desktop:smoke, npm run build:web, npm run build:worker.

После публикации: npm run verify:production -- --revision FULL_COMMIT_SHA --wait 600.

Прод-проверка только читает публичные ресурсы и делает анонимный запрос MCP. Она не создаёт пользовательские данные, не выполняет платёж и не проверяет RLS вместо двух тестовых аккаунтов.
